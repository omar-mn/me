Mates

Real-time chat app & infrastructure

Mates is a real-time chat application built with Django and React and structured as a multi-service system rather than a single application container. The system separates Users, Chat, and Frontend responsibilities and combines application services with caching, asynchronous workers, reverse proxies, observability, and a high-availability data layer.

The backend exposes REST APIs and persistent WebSocket communication for authentication, rooms, memberships, and messaging, with 28 documented REST/WebSocket endpoints. Django Channels handles real-time communication, Redis supports the asynchronous and caching layer, and Celery workers handle background processing.

The infrastructure side was designed around failure boundaries and operational visibility: PostgreSQL is deployed with Patroni, etcd, and HAProxy to model database failover; Traefik handles HTTP and WebSocket traffic while Nginx serves frontend assets; Prometheus, Grafana, and Loki provide metrics, dashboards, and centralized logs. GitHub Actions validates the application, builds container images, and publishes versioned artifacts before deployment to Kubernetes through custom manifests.

  • Highly-available PostgreSQL using Patroni, etcd, and HAProxy, with Redis for caching and asynchronous processing
  • Traefik for HTTP/WebSocket traffic and Nginx for frontend static assets
  • Prometheus, Grafana, Loki, cAdvisor, node-exporter, nginx-exporter, and Django metrics for observability
  • GitHub Actions for testing, image builds, and versioned publishing
  • Two Celery workers for background processing
  • Deployed to Kubernetes through custom Minikube manifests

Private RKE2 Kubernetes Platform

Self-hosted, production-style platform

Built during the Mosalam DevOps internship as a private Kubernetes platform rather than a single application deployment. The cluster runs RKE2 across a multi-network lab environment with a 3-node highly-available control plane backed by etcd. Control-plane, pod, and NAT traffic are separated across dedicated network interfaces and address ranges.

Cilium provides the cluster networking layer with eBPF, native routing, and kube-proxy replacement. Application traffic is exposed through Gateway API and Traefik. Because the environment has no cloud load balancer, kube-vip provides the Kubernetes API VIP, while Cilium LoadBalancer IPAM and L2 announcements provide LoadBalancer-style service exposure inside the private network.

Longhorn provides dynamically provisioned persistent storage, and Argo CD is deployed and actively synchronizing application state from Git. The platform is being extended with Argo Rollouts for progressive delivery, failure testing, and platform documentation.

  • 3-node HA control plane with embedded etcd and kube-vip for the Kubernetes API VIP
  • Cilium networking with eBPF, native routing, and kube-proxy replacement
  • Cilium LoadBalancer IPAM and L2 announcements for private LoadBalancer exposure
  • Gateway API and Traefik for application traffic
  • Longhorn for dynamically provisioned persistent storage
  • Argo CD for Git-based application synchronization
Implemented: HA control plane, Cilium networking, private LoadBalancer exposure, Traefik / Gateway API, Longhorn, and Argo CD. In progress: Argo Rollouts, progressive delivery testing, failure testing, and platform documentation.
